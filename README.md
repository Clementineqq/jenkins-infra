# jenkins-infra

Docker-обёртка для Jenkins controller: образ на базе `jenkins/jenkins:lts`
плюс `docker-cli`, и `docker-compose.yml`, который поднимает Jenkins.

Нужен, чтобы контроллер разворачивался на чистой машине предсказуемо. Сам Jenkins здесь — только
контроллер: сборки идут на отдельном агенте, у контроллера нет доступа
к Docker-сокету.

## Состав

```
Dockerfile           jenkins/jenkins:lts + docker-cli, запуск от пользователя jenkins
docker-compose.yml   controller: образ my-jenkins:lts, порты 8081/50000,
                     внешний том jenkins_home
```

## Требования

- Docker Engine и Docker Compose v2 — на машине, где живёт контроллер
- отдельная машина или VM для агента сборки: Docker + SSH-доступ к стендам

## Запуск

```bash
# 1. том объявлен external — создаём заранее
docker volume create jenkins_home

# 2. собрать образ и поднять контроллер
docker compose up -d --build

# 3. дождаться старта и забрать initial admin password
docker compose logs -f jenkins
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

# 4. открыть веб-интерфейс
#    http://localhost:8081
```

После входа: **Manage Jenkins → Plugins** — поставить минимум

| Плагин | Зачем |
|---|---|
| Docker Pipeline | шаг `withDockerContainer` в общей библиотеке |
| Git / GitHub | работа с репозиториями и вебхуками |
| Credentials Binding | `withCredentials` для секретов |
| Slack Notification | уведомления о сборках |

Затем **Manage Jenkins → System → Jenkins URL** — указать адрес, по которому
GitHub будет присылать вебхуки.

## Порты

| Порт | Назначение |
|---|---|
| `8081` → `8080` | веб-интерфейс. На хосте специально не 8080: этот порт обычно занят приложением (локальный `docker compose` из VoidSounds) |
| `50000` | JNLP-подключение агентов |



### Контроллер без Docker-сокета

Раньше сборки шли прямо на контроллере через смонтированный
`/var/run/docker.sock` — это фактически root на хосте для любого, кто может
запустить пайплайн. Теперь контроллер только раздаёт задачи, а сборка идёт
на отдельном агенте. Минус схемы: без агента не собирается ничего, сам
контроллер собрать образ не может.

`docker-cli` в образе остался с прежней схемы, когда сборки шли на
контроллере. Сейчас он не используется: сокет не смонтирован, демона внутри
контейнера нет. Убрать его из `Dockerfile` — в планах.

### Образ собирается локально, а не тянется из registry

Пока контроллер один, проще: `docker compose up -d --build` всегда даёт
актуальную версию. При нескольких инстансах логичнее собирать и публиковать
образ в GHCR.

### Агент и стенды на одной VM

Агент, staging и production временно живут на одной VM — так проще отлаживать
всю цепочку. Разнести их по разным машинам — в планах.

## Агент сборки

Агент `docker-build` — ВМка с Docker и SSH-ключом до стендов,
подключён к контроллеру по SSH. У него две метки: `docker` (CI-сборки) и
`docker-build` (деплой). Обе метки висят на одном узле, поэтому и сборка,
и деплой выполняются на этой VM, а не на контроллере.

Настройка выполняется вручную (Manage Jenkins → Nodes → New Node), поэтому в
репозитории её нет. Автоматическое создание через Ansible в планах.

## Webhook из GitHub в локальный Jenkins

Контроллер запущен в Docker на локальной машине без публичного IP, поэтому
GitHub физически не может доставить webhook.
Для этого я поднял временный туннель через сервис CloudPub (аналог ngrok):
клиент публикует локальный порт `8081` как HTTPS-адрес вида
`https://<поддомен>.cloudpub.ru`.

Дальше в GitHub: **Settings → Webhooks → Add webhook**

- Payload URL: `https://<поддомен>.cloudpub.ru/github-webhook/`
- Content type: `application/json`
- Secret: значение из Jenkins Credentials (проверка подписи payload)
- Events: *Just the push event*

### Ограничения этого решения

- адрес туннеля меняется при перезапуске, после чего вебхук приходится
  обновлять; стабильный URL даёт именованный туннель (cloudflared) или
  собственный внешний адрес;
- пока туннель поднят, Jenkins доступен из интернета;
- если туннель не поднят, вебхук не доставляется — сборку подхватывает
  периодическое сканирование multibranch-джобы (
  `Started by ... Branch indexing`).

Это лабораторное решение. В production Jenkins ставится за reverse proxy с
TLS, вебхук приходит на постоянный адрес и подписан секретом.

## Безопасность

- анонимный доступ выключен, права — `Logged-in users can do anything`;
- регистрация пользователей запрещена;
- секреты хранятся в Jenkins Credentials, а не в пайплайнах и не в репозитории;
- контроллер не имеет доступа к Docker-сокету хоста;
- туннель поднимается только на время работы и закрывается после сессии.

## Полезные команды

```bash
docker compose ps                  # состояние контроллера
docker compose logs -f jenkins     # логи
docker compose restart             # перезапуск
docker exec jenkins jenkins --version
docker volume inspect jenkins_home # где лежат данные
```

## Ограничения

- [ ] агент `docker-build` настраивается вручную, автоматического создания
      (Ansible) нет
- [ ] `docker-cli` в образе контроллера больше не нужен — убрать
- [ ] нет TLS и reverse proxy: Jenkins доступен по HTTP в локальной сети,
      наружу — только через временный туннель
- [ ] джобы и креденшелы создаются руками
- [ ] бэкап `jenkins_home` выполняется вручную, по расписанию не настроен
- [ ] контроллер один, резервирования нет
- [ ] агент и оба стенда на одной VM, разделение по машинам не сделано
